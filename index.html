REBU-5892 REBU-6227 Puestos y Cargos — el cargo deriva su nombre del puesto · UAT co.2
10 / 10 ✓▼
Qué certifica este bloque
La épica introduce el Puesto como entidad padre del Cargo, y el cargo deja de tener nombre propio: lo deriva de su puesto. Eso convierte a REBU-5892 en un cambio transversal, no en una feature de catálogo. Estos flujos verifican que el nombre derivado llega correcto a cada consumidor aguas abajo — el listado de Cargos (INT-081), el organigrama y sus plazas vacantes (REG-088), la búsqueda tras pasar de columna propia a join (REG-090) y el catálogo de campos de las plantillas (INT-086, REG-089) — y que las reglas de integridad del catálogo se sostienen: un puesto con cargos no se borra, y dos nombres que solo difieren en mayúsculas o tildes son el mismo puesto.

E2E-INT-081
Renombrar un puesto cambia el nombre de sus 2 cargos sin tocarlos
@api@colaboradores@regression@critical
PASS
Documentado enREBU-6227 · flujo E2E-INT-081 · HUs REBU-5895 REBU-5899 REBU-5903 REBU-5904
AmbienteUAT co.2 · app-rebu-portal-03-uat.azurewebsites.net
Precondicionesun puesto recién creado con descripción, y dos cargos dentro de él. Ningún id quemado: el puesto se resuelve por nombre.
Regla evaluadaEl cargo no tiene nombre propio: lo deriva de su puesto vía PositionNameHelper (REBU-6112). Renombrar el puesto debe cambiar el nombre visible de todos sus cargos sin tocar ninguno, y sin alterar sus códigos. Importa porque el fallback legacy a Position.Name sigue vivo: un consumidor que aún lo lea mostraría el nombre viejo sin romperse, y este caso es el que lo delata desde afuera.
Setup1. POST /api/dashboard/2/job-titles con nombre único y descripción → devuelve { id, code }.
2. POST /api/dashboard/2/job-positions ×2 con jobTitleId → dos cargos dentro del puesto.
3. Guardar como línea base el código del puesto y el código de cada cargo.
Pasos1. Leer el listado de Puestos → Esperado: el puesto figura con N.º de cargos = 2.
2. PUT /job-titles/{id} con el nombre nuevo → Esperado: 204.
3. Leer el listado de Cargos por el nombre nuevo → Esperado: los dos cargos aparecen con cargo y jobTitleName actualizados y su jobTitleId intacto.
4. Verificar los códigos → Esperado: el código de cada cargo y el del puesto no cambian.
5. Buscar por el nombre anterior → Esperado: ningún cargo lo resuelve todavía.
6. Leer el detalle del puesto → Esperado: nombre nuevo, código y descripción intactos, contador en 2.
Resultado esperadoel nombre del puesto es la única fuente del nombre del cargo, y el renombre se refleja en catálogo y detalle sin tocar ningún cargo.
Resultado obtenidoEl puesto se creó con código autoasignado y quedó con positionsCount: 2. El PUT respondió 204 y los dos cargos pasaron a mostrar el nombre nuevo en cargo y jobTitleName, conservando jobTitleId, su código de cargo y el código de puesto. La búsqueda por el nombre anterior devolvió cero cargos — no quedó rastro del fallback legacy. El detalle del puesto conservó descripción y contador. ✅

E2E-INT-081b
Un puesto con cargos asociados no se puede borrar, y sin ellos sí
@api@validacion
PASS
Documentado enREBU-6227 · flujo E2E-INT-081b · HU REBU-5900
AmbienteUAT co.2 · app-rebu-portal-03-uat.azurewebsites.net
Precondicionesun puesto con un cargo dentro.
Regla evaluadaUn puesto solo se elimina si no tiene cargos. La guarda debe funcionar en los dos sentidos — rechazar mientras haya cargos y permitir cuando ya no los haya — y el rechazo debe explicar el motivo, no ser un 409 genérico que obligue a adivinar.
Setup1. Crear el puesto por API.
2. Crear un cargo dentro de él con jobTitleId.
Pasos1. DELETE /job-titles/{id} con el cargo vivo → Esperado: 409 y el mensaje menciona que tiene cargos asociados.
2. DELETE /job-positions/{id} para borrar el cargo → Esperado: OK.
3. DELETE /job-titles/{id} otra vez → Esperado: 204.
Resultado esperadola integridad referencial del catálogo se sostiene, y el error es legible para quien lo recibe.
Resultado obtenidoCon el cargo vivo el borrado devolvió 409 con “No se puede eliminar el puesto porque tiene cargos asociados.” — motivo explícito, no un código pelado. Tras borrar el cargo, el mismo DELETE respondió 204. ✅

E2E-REG-088
El organigrama muestra el nombre derivado del puesto y lo actualiza al renombrarlo
@api@colaboradores@regression@critical
PASS
Documentado enREBU-6227 · flujo E2E-REG-088 · HUs REBU-5899 REBU-5904
AmbienteUAT co.2 · app-rebu-portal-03-uat.azurewebsites.net
Precondicionesdos puestos y una jerarquía de dos niveles con plazas vacantes: un cargo padre y un cargo hijo que cuelga de él.
Regla evaluadaREBU-6112 migró tres queries del organigrama a PositionNameHelper: la jerarquía, el detalle de nodo y las plazas vacantes. El propio dev marcó como riesgo (hallazgo G1) que a alguno le faltara el Include(JobTitle), en cuyo caso el nodo saldría con nombre vacío en vez de romperse. Se usan plazas vacantes a propósito: ejercita la derivación y la jerarquía sin depender del ocupante, y de paso cubre el tercer query.
Setup1. Crear dos puestos por API (“Jefatura” y “Operativo”).
2. Crear el cargo padre en el primero, sin jefe.
3. Crear el cargo hijo en el segundo, con parentPositionId apuntando al padre.
Pasos1. GET /api/dashboard/2/org-chart y buscar ambos nodos en el árbol → Esperado: cada uno muestra el nombre de su puesto, y el nombre no viene vacío.
2. Verificar la jerarquía → Esperado: el hijo está entre los children del padre y el padre reporta al menos 1 subordinado directo.
3. Verificar las plazas → Esperado: ambas figuran isVacant: true y sin ocupante residual.
4. Renombrar el puesto padre y releer el organigrama → Esperado: el nodo refleja el nombre nuevo, su código no cambia, el hijo conserva el suyo y la jerarquía sobrevive.
Resultado esperadoningún nodo del organigrama muestra el nombre viejo ni un valor nulo tras el refactor.
Resultado obtenidoLos dos nodos aparecieron en el árbol con el nombre de su puesto y sin campos vacíos. El hijo colgaba del padre y el padre reportó su subordinado directo. Ambas plazas se marcaron vacantes con occupantName: null. Tras el renombre, el nodo padre mostró el nombre nuevo conservando su código, el hijo mantuvo el propio — no heredó el del padre — y la relación padre-hijo se mantuvo. ✅
StatusPASS

E2E-REG-090
La búsqueda de cargos ignora mayúsculas y tildes después del join
@api@validacion@regression
PASS
Documentado enREBU-6227 · flujo E2E-REG-090 · HUs REBU-5897 REBU-5903
AmbienteUAT co.2 · app-rebu-portal-03-uat.azurewebsites.net
Precondicionesun puesto cuyo nombre lleva tilde y mayúscula (“Técnico Eléctrico”) y un cargo dentro de él.
Regla evaluadaEl buscador filtraba con Like sobre Position.Name — una columna propia con collation CI_AI, insensible a mayúsculas y acentos. REBU-6112 lo movió a un join contra JobTitle.Name. Un join que no preserve la collation vuelve la búsqueda sensible a tildes y el usuario deja de encontrar sus cargos — sin ningún error: solo resultados vacíos, que es la peor forma de fallar.
Setup1. Crear el puesto con tildes por API.
2. Crear un cargo dentro de él.
Pasos1. Buscar el término sin tildes y en minúsculas → Esperado: encuentra el cargo.
2. Buscar el mismo término en mayúsculas → Esperado: lo encuentra.
3. Buscar un fragmento parcial → Esperado: devuelve coincidencias.
4. Repetir la búsqueda sin tildes en el listado de Puestos → Esperado: mismo comportamiento.
5. Buscar un término inexistente → Esperado: listado vacío, sin error.
Resultado esperadola búsqueda conserva su semántica insensible a acentos y mayúsculas tras pasar de columna propia a join.
Resultado obtenidoLas cuatro variantes —sin tildes, en minúsculas, en mayúsculas y fragmento parcial— encontraron el cargo, y el listado de Puestos se comportó igual. El término inexistente devolvió lista vacía sin error. La collation CI_AI sobrevivió al join. ✅

PASS
Documentado enREBU-6227 · flujo E2E-REG-090b · HU REBU-5895 (AC7, AC8)
AmbienteUAT co.2 · app-rebu-portal-03-uat.azurewebsites.net
Precondicionesun puesto ya creado con tildes en el nombre.
Regla evaluadaAC8 de REBU-5895: la comparación de nombres ignora mayúsculas, tildes y espacios de más. Lo que este caso cruza es que la unicidad y la búsqueda usen la MISMA normalización: si una ignora tildes y la otra no, el catálogo se llena de duplicados que el buscador presenta como si fueran el mismo puesto, y nadie entiende por qué hay dos.
Setup1. Crear el puesto con el nombre canónico (con tildes).
Pasos1. Intentar crear otro puesto con el mismo nombre sin tildes y en mayúsculas → Esperado: el BE lo rechaza.
Resultado esperadounicidad y búsqueda comparten normalización: no se puede crear un puesto que solo difiera en mayúsculas o acentos.
Resultado obtenidoEl intento devolvió 409 con “Ya existe un puesto con ese nombre”, que es el AC7 literal. La normalización de la unicidad coincide con la de la búsqueda del caso anterior. ✅

E2E-INT-086a
El grupo Puesto trae sus 4 campos y Cargo salió del grupo Colaborador
@ui@documentos@critical
PASS
Documentado enREBU-6227 · flujo E2E-INT-086a · HUs REBU-5907 REBU-5908 REBU-5924 REBU-5939
AmbienteUAT co.2 · app-rebu-portal-03-uat.azurewebsites.net · viewport 1440×900
Precondicionesacceso a Documentos › Plantillas con permiso de creación.
Regla evaluadaLo que produce el catálogo de Puestos tiene que aparecer como insumo consumible en el módulo de Documentos, que es otro módulo y otra HU. AC1 y AC2 de REBU-5907 exigen un grupo Puesto con cuatro campos; el AC6 exige que Cargo se haya movido, no duplicado — si quedara en los dos grupos, el usuario tendría dos campos con el mismo nombre y distinto origen. El AC9 pide que el buscador del desplegable los encuentre.
Setup1. Documentos › Plantillas › Nueva Plantilla.
2. Abrir el desplegable Insertar Campo y leer sus grupos en orden del DOM.
Pasos1. Leer los grupos del desplegable → Esperado: existen PUESTO y COLABORADOR.
2. Leer el contenido del grupo Puesto → Esperado: exactamente Puesto, Descripción del puesto, Cargo, Jefe directo, en ese orden.
3. Leer el grupo Colaborador → Esperado: no contiene Cargo.
4. Verificar que el grupo Colaborador se pobló con los campos de REBU-5908 → Esperado: más de 10 campos.
5. Escribir “puesto” en el buscador del desplegable → Esperado: encuentra Descripción del puesto.
Resultado esperadoel catálogo de campos expone el grupo Puesto completo y el campo Cargo vive en un solo lugar.
Resultado obtenidoEl desplegable expuso nueve grupos: COLABORADOR, PUESTO, REMUNERACIONES, DEDUCCIONES MENSUAL, DEDUCCIONES VARIABLE, ACUMULADOS DEL AÑO, EMPRESA, GENERAL y DESCUENTOS CÍCLICOS. El grupo PUESTO trajo exactamente los cuatro campos del AC2 en orden, y COLABORADOR —con 21 campos— ya no ofrece Cargo: se movió sin duplicarse. El buscador filtró correctamente. ✅

01 — grupo PUESTO con sus 4 campos y COLABORADOR sin Cargo
02 — el buscador del desplegable filtra por "puesto"

E2E-REG-089
Una plantilla con {{Cargo}} se guarda, se reabre y conserva el campo
@ui@documentos@regression@critical
PASS
Documentado enREBU-6227 · flujo E2E-REG-089 · HU REBU-5907 (AC7)
AmbienteUAT co.2 · app-rebu-portal-03-uat.azurewebsites.net · viewport 1440×900
Precondicionesuna plantilla nueva con el campo Cargo insertado y texto que lo acompañe.
Regla evaluadaEl campo Cargo vivía en el grupo Colaborador y REBU-5907 lo movió al grupo Puesto. El AC7 promete que las plantillas que ya lo tenían insertado “siguen funcionando sin ningún cambio”. Si el identificador interno del token hubiera cambiado al moverlo de grupo, todas las plantillas de contrato productivas quedarían con un placeholder literal — y eso solo se ve al generar, nunca al guardar. De ahí que el caso verifique que el token se reabre como nodo propio del editor y no disuelto en el texto.
Setup1. Nueva Plantilla con nombre.
2. Escribir el texto de la constancia.
3. Insertar el campo Cargo desde el grupo Puesto.
Pasos1. Verificar el cuerpo antes de guardar → Esperado: contiene {{Cargo}}.
2. Guardar la plantilla → Esperado: guarda sin error.
3. Volver al listado y reabrirla → Esperado: aparece y abre.
4. Leer el cuerpo → Esperado: el token y el texto que lo acompaña siguen intactos.
5. Inspeccionar el token → Esperado: es un nodo propio del editor, no texto literal.
Resultado esperadomover el campo de grupo no rompe las plantillas que ya lo usaban.
Resultado obtenidoLa plantilla guardó y reabrió con Por medio de la presente se hace constar el cargo de: {{Cargo}} intacto. El token se reabrió como <span data-lexical-text="true"> con su estilo de campo — nodo propio del editor, no texto disuelto. El identificador interno sobrevivió al cambio de grupo. ✅
Evidencia
01 — token Cargo insertado, antes de guardar
02 — plantilla reabierta con el token intacto
